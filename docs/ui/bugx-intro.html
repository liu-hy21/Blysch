Part 01b · 价值和场景

为什么用 BugX · 什么时候该排查

为什么要用它

  • 先查数据，再动代码——90% 是表没数/导出断/口径不一致，查清根因再动手。
  • 减少反复争论——用同一套链路 + 实查证据，用查询结果对齐。
  • 输出规范的排查报告——§A.1 一句话 + §A.2 链路图，不是「应该是数据问题」。

什么时候用它

  • 页面/接口数据不对、缺数、数值异常
  • 产品说「和计算器/常识对不上」（如案例 003）
  • 同一指标多出口不一致（顶部率 vs 下钻明细）
  • 只问「某张表有没有数」——可直查，不必走全流程
❌ 不必用：纯 UI 文案/颜色、权限鉴权、排序分页导出样式——这些不是数据链路 bug。
💡 记住这句
解决的是「查不清、难对齐、没留档」；看见「数」不对就可以用 BugX。

Part 04 · 怎么写报告

先写结论，再用证据说明

结论只有一句；下面用现象、原因、范围、改法逐条补充。结构如下（具体数字与表名见案例章节）：

▲ 一句话结论 · §A.1
是否代码 bug + 根因在哪一步 + 下一步改什么（数仓 / 导出 / 配置，或确认非平台问题）。
分论点一 · 现象和原因
现象：接口返回什么、页面看到什么，用数字写清。
原因：已验证的根因，不是猜测。
分论点二 · 时间和断点
时间：查询窗口、起止日期。
断点：链路第几步、哪一层有数 / 没数 / 口径不一致。
分论点三 · 改法
能执行的下一步：补跑任务、修正节点 SQL、补导出分区，或说明无需改代码。
Part 04 · 出报告前自检

出报告前：检查容易遗漏的地方

检查项问自己❌ 常见问题✓ 改成这样
现象 量化了吗？ 「某个指标不对」 「汇总值 0.97，下钻 4 条，窗口内总数 2335」
原因 根因还是猜测？ 「应该是数据没同步吧」 「数仓表有 4 条，查询库同区间 0 条 → 导出断档」
时间 日期区间明确吗？ 「最近几天」 「查询窗口 7 天，起止日期写清楚」
断点 第几步、哪张表？ 「数仓有问题」 「第③步有数、第②步无数；或第④步的节点 SQL 口径不一致」
改法 下一步能动手吗？ 「让数据同学看看」 「补跑导出任务 + 修正数仓节点 SQL」
💡 记住这句
先把结论写清楚，再逐项补充量化现象、已验证原因、具体改法——避免把措施当结论、把空泛说法当方案。
Part 05

四个真案例

docs/bugs/00-历史排查案例.md
建议讲法：001 查不到 → 002 有数无完整率 → 003 综合 → 004 日期选不到最新

Case 001

车型数据质量监测 · CAN分类指标查询页面：配置正常，页面没数。8 月查不到精确车系码 C589。跟国标报文表无关。

结论

26 号改配置；27 号配置同步到云器；28 号在页面上能看到数据。28 号再看。
Case 002

车型数据质量监测 · CAN分类指标查询页面：有有效率、及时率，没有完整率。C589 全量车 xml_version=20200000000000、date=2026/08/27、duration=1，状态「未达标」。

结论

三个率看的不是同一批信号。有效率、及时率看车上实际采到的，采到就能算。完整率只看清单里标了「周期采集」的：该采的有没有采到。这个 XML 版本全量挂载里一项周期采集都没有，完整率就空着。要算出完整率，需要业务人员去采集平台，给全量挂载补上周期采集信号。
Case 003

单车数据异常分析 · 国标：顶部及时率、间隔率对了，明细对不上。VIN=LVRHDCEM9SN010167，7 日，08/19：gbTmyRate=0.97，gbDelayRate=0.99830，总数 2335；gbRealtimeDelayMessage 4 条；gbDelayMessage 0 条。

① 及时率 97% vs 明细 4 条

率：dwd_vhc_data_quality_gb_time_diff 全量 75/2335。明细：dwd_vhc_data_quality_gb_report_abnormal_data_detail_di rank=1 每天每车 1 条。
改：去掉 rank=1 → 改 Hive SQL 任务。

② 间隔率 99.83% vs 明细 0 条

Hive dwd_vhc_data_quality_gb_delay_data 有 4 条；Doris dwd_vhc_data_quality_gb_delay_message_di 08-13~19 无数据。
改：补分区 + 补跑同步任务。Hive 源表不用改。
Case 004

单车查询页面：VIN=LS5A3DME6SA200061，近 7 天日期只能选到 2026-08-11（近 1 天只能选到 2026-08-04）。vehicle-index duration=7、pDay=2026-08-11 看起来没数据。

结论

不是接口的事。这辆车 08-05 没再报国标、CAN 也没采到，近 1 天只能选到 08-04。能选到 08-11 是故障码还在，打开国标和 CAN 是空的。
Part 06 · 实操

在对话框里怎么使用

打开 agent 对话框，输入 @bugx 或直接描述问题；把症状 + kb 路径一次说清，AI 会按六步流水线执行。

① 完整排查 · 粘贴到对话框（案例 003）
用 bugx 排查：国标单车 VIN=LVRHDCEM9SN010167，date=2026/08/19，duration=7。gbTmyRate=0.97 但 gbRealtimeDelayMessage 只有 4 条；gbDelayMessage 为 0。kb 在 docs/architecture/kb/02-单车数据查询.md
② 只查表 · 粘贴到对话框
查一下 Doris dw.dwd_vhc_data_quality_gb_delay_message_di，VIN=LVR…，p_day 在 2026-08-13 到 2026-08-19 有没有数据。
对话框里配合 AI 时注意

不用会 SQL

你负责指 kb、说症状、填 Cookie；看 §A.1 和关键数字即可。

NDH 时要填 Cookie

AI 问到时提供工号 + Cookie，用于拉取节点 SQL 并保存到 docs/ndh/。仅当次使用，不写 git。

等报告再动手

看 §A.1「是否代码 bug」再决定改 Java 还是数仓。案例 003 改法都在数仓侧。

kb 和 NDH SQL 分工

kb 指路；NDH SQL 是实际逻辑。不能把 kb 一句话当已验证结论。
Part 07 · 收尾

记住这三条

  • ① 先查数据，再查代码——页面上的数，多半来自某张表；表里没有或断了，改代码也无法解决。
  • ② 从接口往上追溯，证据够了就停止探索——接口 → 数据库 → 数仓任务；能对上根因就写报告，不必每张表都扫一遍。
  • ③ 先说结论，再摆证据——一句话讲清楚「是不是 bug、断在哪」；下面用关键数字和链路图补充说明结论。

开始排查时记住两件事：把症状说具体（哪个接口、哪个字段、期望 vs 实际），告诉 AI 知识库在哪。
